# ADR 0002 — Language stack: Python everywhere except the frontend

- **Status:** Superseded by [ADR 0003](0003-polyglot-stack.md)
- **Date:** 2026-05-05
- **Superseded:** 2026-05-05 (same session — see ADR 0003 for context)
- **Deciders:** Founding team

## Context

Pactline does heavy work in three areas where ecosystem maturity dwarfs
language preference:

1. **AI orchestration.** LangGraph, LiteLLM, the Anthropic / OpenAI /
   Azure SDKs, prompt evaluation tooling, and the Pydantic-based
   structured-output ecosystem are all materially better in Python
   than in any other mainstream backend language.
2. **Document parsing.** PyMuPDF, pdfplumber, Docling, LibreOffice
   bindings, and the OCR ecosystem (Tesseract wrappers, layout
   parsers) are Python-first.
3. **Workflow orchestration.** Temporal Python SDK is first-class.
   Temporal also has Go, TypeScript, Java, and .NET SDKs, but the
   rest of the system pulls toward Python.

The frontend is unavoidably TypeScript: React 19, Next.js 15, Tailwind,
shadcn/ui. There is no realistic alternative for the user-facing
surface.

The question is therefore not "what language" but "how many languages."
Mainstream alternatives:

- **Python + TypeScript** (this ADR's choice): two languages, both
  load-bearing, neither niche.
- **Go + TypeScript:** stronger concurrency story, but cedes the
  AI / document / workflow ecosystem advantages and forces shelling
  out to Python anyway for the heavy lifting.
- **Java / Kotlin + TypeScript:** similar tradeoff to Go, with more
  ceremony and less startup velocity.
- **Rust + TypeScript:** premature for a Phase 0 product; ecosystem
  for AI and document parsing is not there yet.
- **Pure TypeScript (Node + Next.js):** unifies the language, but
  Node's AI / document / workflow ecosystem is materially behind
  Python's, and Temporal's TypeScript SDK is solid but not the
  reference SDK.

## Decision

Pactline is **Python 3.12+** for everything backend (api, worker, all
`pactline_*` packages) and **TypeScript / Next.js 15 / React 19** for
the frontend (`apps/web`).

There are exactly two languages in the codebase. Adding a third
requires an ADR.

The frontend consumes the API via types generated from the FastAPI
OpenAPI spec (`openapi-typescript`). Generated types live at
`apps/web/src/api/types.ts` and are regenerated by
`make generate-types`. CI fails if generated types are stale.

## Consequences

- The team only needs to be fluent in two languages. Hiring is easier
  than for polyglot stacks.
- AI, document parsing, and workflow code stay close to the libraries
  they depend on — no IPC, no language bridging.
- Frontend types are derived, not written by hand. Drift between the
  API and the UI is a CI failure, not a runtime bug.
- Python's GIL and async-runtime model is a constraint we accept.
  Pactline is async end-to-end (FastAPI, async SQLAlchemy, async
  Temporal client). CPU-bound work (document parsing, image OCR) runs
  in Temporal activities and uses worker concurrency, not threading
  inside the API process.
- Performance-critical edges that fall outside async-Python's
  wheelhouse (e.g., high-throughput indexing, sub-100ms semantic
  search at scale) may eventually need a service in another language.
  That decision will require an ADR and is not anticipated before
  Phase 4.

## Alternatives considered

See Context. The decision is to accept Python's runtime constraints in
exchange for ecosystem leverage on the surfaces that matter most
(AI, documents, workflows).
